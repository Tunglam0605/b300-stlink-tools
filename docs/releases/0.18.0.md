# B300 ST-Link Tools v0.18.0

## Simplified production UX

- Replaces the previous debugger-heavy production shell with five clear primary pages: **PROGRAM / MONITOR / DEBUG / DEVICE / SETTINGS**.
- PROGRAM reuses the existing validated B300 flash/factory safety path and keeps advanced details progressively disclosed.
- MONITOR remains the dedicated zero-halt realtime observation workflow and stays separate from interactive debug.
- DEBUG is now centered on **VS Code + Cortex-Debug** instead of turning B300 into a full IDE.
- Opening DEBUG or switching pages does not start OpenOCD/GDB, acquire the debug HardwareSession, reset the target, or halt the MCU.

## VS Code Debug Bridge

- Adds explicit **LOCAL / GATEWAY / CLIENT** roles.
- LOCAL: B300 starts private loopback OpenOCD and generates an attach-only Cortex-Debug profile for the selected local ELF/AXF.
- GATEWAY: OpenOCD GDB and TCL remain bound to `127.0.0.1`; Telnet is disabled. TCL stays Gateway-local for run-state restoration.
- CLIENT: only GDB is forwarded through the authenticated SSH session. Source and ELF/AXF remain on the Client machine; no Client-side ST-Link or OpenOCD installation is required.
- Cortex-Debug profiles use `request=attach`, `servertype=external`, loopback-only GDB targets, required hardware breakpoints and hardware watchpoints.
- Existing run-state safety is preserved: if the target was running before an interactive debug session, B300 attempts to restore RUNNING when GDB disconnects or the bridge is stopped while the target is left halted.

## Managed ARM GDB runtime

- B300 release bundles now carry a pinned, SHA-256 verified **GNU Arm GDB 15.2.1-1.1** runtime for Windows x64, Ubuntu x64, and Ubuntu ARM64.
- The release builder downloads the trusted xPack GNU Arm Embedded package, verifies both the upstream checksum and B300 trust anchor, extracts it with bounded archive validation, then stages only GDB plus required host runtime files and upstream notices.
- GCC, G++, linker, target C libraries and target build toolchain files are intentionally excluded. B300 remains a programmer/debug bridge, not an application build environment.
- Managed GDB is smoke-tested before packaging and is resolved before system PATH fallbacks, so a clean machine no longer needs a separately installed Arm GNU Toolchain merely to debug through B300.

## Remote programming safety foundation

- Adds a content-addressed remote firmware manifest with basename, size, SHA-256, target, board and privilege validation.
- Standard remote Application programming reuses the existing `B300Service.inspect_image -> inspect_target -> plan -> flash` safety transaction.
- No `FULL_ERASE`, `MASS_ERASE` or arbitrary raw-write operation is exposed.
- Intel HEX is the only remote executable programming format currently enabled because it is backed by the existing address-range validation path. BIN/ELF/AXF remain transfer-contract formats only and fail closed for execution until equivalent address validation exists.
- Remote Bootloader programming remains disabled pending a separate elevated authorization/audit workflow.

## Preserved safety boundaries

- Normal Application programming does not write Bootloader sectors 0-2 and does not mass erase.
- OTA metadata and Option Byte / WRP safety policy are unchanged.
- `HardwareSession` arbitration remains authoritative across flash, monitor and interactive debug.
- Live Monitor remains zero-halt and read-only.
- Interactive debug begins only after an explicit operator action.
- Remote debug exposes no raw OpenOCD ports to the LAN/Internet; GDB is carried through authenticated SSH and TCL remains private.

## First-machine setup after v0.18.0

For the standard Windows/Ubuntu debug workflow, the user installs:

1. B300 ST-Link Tools v0.18.0.
2. VS Code.
3. VS Code extension `marus25.cortex-debug` (Cortex-Debug).
4. VS Code extension `ms-vscode.cpptools` is recommended for C/C++ editing/navigation.

B300 supplies/manages OpenOCD and ARM GDB for the supported release architectures. A separate STM32CubeIDE, Keil, STM32CubeProgrammer or system `arm-none-eabi-gdb` installation is not required just to use the B300 VS Code debug bridge.

## Validation target

The release candidate must pass cross-platform CI and native release packaging on Windows x64, Ubuntu x64 and Ubuntu ARM64 before the `v0.18.0` release is promoted. Real-hardware acceptance (ST-Link Application flash, Live Monitor, LOCAL VS Code debug, two-machine GATEWAY/CLIENT debug, target-state restoration, cold power-cycle, and OTA -> ST-Link -> OTA regression) remains the final operator acceptance step.
