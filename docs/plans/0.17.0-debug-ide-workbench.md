# B300 v0.17 Debug IDE Workbench

## Goal

Replace the v0.16 fixed three-column Debug Workstation with an IDE-style workbench inspired by Keil uVision and STM Studio while preserving B300 safety boundaries.

This is a layout/interaction redesign, not a change to target-control, Flash/OTA, OpenOCD, GDB/TCL, or zero-halt monitoring policy.

## UX principles

1. Source/debug context is the center of the screen, not one pane among many.
2. Tool panes are dockable/tabbed and can be shown/hidden without destroying their state.
3. Realtime monitoring and intrusive interactive debug remain visibly separated.
4. The first screen stays simple: select LOCAL/GATEWAY/CLIENT, symbols, connect.
5. Once interactive debug starts, the user enters a persistent engineering workbench similar to a desktop IDE.
6. Dense technical information is available, but secondary information is collapsed into docks/tabs rather than stacked cards.
7. Layout state can later be persisted per user and reset to a known default.

## Pane model

### Center editor area

- Source
- Disassembly
- Trace timeline (future native C++ path)
- Fault location jump target

The center area must keep at least 50% of the horizontal workspace in the default layout.

### Left tool dock

- Symbols
- Call Stack
- Optional Modules/Files later

### Right tool dock

- Locals / Watch
- CPU Registers
- SVD Peripherals
- Target summary

### Bottom tool dock

- Breakpoints
- Live Watch (zero-halt boundary notice while interactive debug is active)
- Memory
- Console
- Technical Log
- HardFault analysis
- FreeRTOS tasks

## Interaction model

### Interactive Debug

Keil-style toolbar actions:

- Run / Continue
- Halt
- Reset
- Step Into
- Step Over
- Step Out
- Break
- Disconnect

Keyboard shortcuts follow IDE conventions where possible. Actions are disabled when invalid for the current target state.

### Zero-halt monitor

The normal Studio realtime monitor remains owned by the setup/studio page. The interactive workbench must never reparent that QWidget.

The bottom LIVE tab inside the workbench is a boundary/status surface, not the normal realtime panel. This preserves the v0.15.2 lifecycle fix.

## Docking requirements

Use `QMainWindow` + `QDockWidget` internally so tool panes can be:

- moved
- tabified
- hidden/shown through a View menu
- restored to a deterministic default layout
- persisted later with `saveState()` / `restoreState()`

The implementation must avoid giant nested fixed `QSplitter` trees as the primary layout mechanism.

## Styling

Direction: engineering IDE rather than dashboard cards.

- compact toolbar height
- small tab bars
- monospace source/register/memory values
- neutral dark gray work area
- restrained status colors
- one accent color for active selection
- amber only for HALT-capable warnings
- red only for failures/destructive/error states
- minimal rounded cards inside the workbench

## Compatibility contract

The new workbench must keep the controller-facing attributes/signals used by the current DebugTab and DebugTabV15 paths:

- `status_bar`
- `toolbar`
- `symbols_pane`
- `callstack_pane`
- `source_view`
- `variables_pane`
- `registers_pane`
- `breakpoints_pane`
- `live_layout`
- `btn_read_memory`
- `memory_addr_input`
- `memory_len_spin`
- `memory_view`
- `console_view`
- `log_view`
- `frame_selected`
- `request_variable_children`
- `step_out_requested`

This allows the layout to change without rewriting the GDB/OpenOCD controller.

## Safety invariants

The UI redesign MUST NOT change:

- Flash sector protection or metadata policy
- Option Bytes policy
- HardwareSession locking
- target state restoration
- GDB/TCL loopback exposure policy
- Safe TCL allow-list
- zero-halt Live Monitor behavior
- LOCAL/GATEWAY/CLIENT transport ownership
