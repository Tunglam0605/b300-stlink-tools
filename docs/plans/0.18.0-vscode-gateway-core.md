# B300 v0.18 — VS Code / Gateway Core

## Goal

B300 v0.18 moves interactive debugging out of the PySide6 application and into
VS Code + Cortex-Debug. B300 remains the ST-Link safety/control plane.

## Roles

### LOCAL

`VS Code -> GDB -> 127.0.0.1:<gdb> -> OpenOCD -> ST-Link -> STM32F407`

B300 starts OpenOCD on loopback and owns the long-lived `DEBUGGING`
`HardwareSession` lease. VS Code owns GDB and the interactive debugger UI.
B300 also keeps a private loopback TCL endpoint only for `RemoteDebugGuard` so a
target that was running before debug can be resumed if GDB disconnects while it
is halted. TCL is never exposed to VS Code or the network.

### GATEWAY

`Gateway OpenOCD 127.0.0.1:<gdb> -> ST-Link -> STM32F407`

The Gateway never publishes OpenOCD directly to LAN/Internet. A Client reaches
GDB through authenticated SSH local forwarding. Gateway TCL remains local-only
and is used exclusively for run-state restoration.

### CLIENT

`VS Code -> 127.0.0.1:<dynamic> -> SSH -> Gateway 127.0.0.1:3333 -> OpenOCD`

The B300 Client only opens a loopback SSH GDB forward. It does not proxy GDB
packets in Python, does not forward TCL and does not need local ST-Link access.

## Backend API for frontend integration

Primary module: `b300_core.vscode_bridge`

- `VsCodeDebugBridge.start_local(probe, gdb_port=3333, tcl_port=6666)`
- `VsCodeDebugBridge.start_gateway(probe, gdb_port=3333, tcl_port=6666)`
- `VsCodeDebugBridge.start_client(remote_session, remote_gdb_port=3333, local_gdb_port=0)`
- `VsCodeDebugBridge.state`
- `VsCodeDebugBridge.profile(program_relative=..., gdb_path=...)`
- `VsCodeDebugBridge.stop()`
- `VsCodeExternalProfile.write_launch_json(workspace)`
- `launch_vscode(workspace)`

Read-only prerequisite inspection is provided by:

- `b300_core.vscode_environment.inspect_vscode_environment()`

Frontend must call start/launch APIs only after explicit operator actions. Merely
opening the Debug page must not start OpenOCD, SSH forwarding or VS Code.

## Target run-state guard

LOCAL and GATEWAY start OpenOCD with:

- GDB on loopback
- TCL on loopback
- Telnet disabled

After OpenOCD becomes ready, B300 captures the initial target state through the
existing `RemoteDebugGuard`. OpenOCD output is observed for GDB connect/drop
events. If the board was initially `running` and GDB drops while the target is
`halted`, B300 resumes it. `VsCodeDebugBridge.stop()` performs a final restoration
check before stopping OpenOCD and releasing the `DEBUGGING` HardwareSession.

This preserves the existing robot run-state cleanup invariant without putting
TCL in the Client data path.

## Cortex-Debug contract

Generated profiles use:

- `type = cortex-debug`
- `request = attach`
- `servertype = external`
- `gdbTarget = 127.0.0.1:<local port>`
- hardware breakpoints/watchpoints required

B300 does not implement source browsing, Watch, Call Stack, Registers,
Disassembly or SVD UI in the primary production flow.

## Remote programming foundation

Primary module: `b300_core.remote_programming`

The transport contract carries a content-addressed manifest containing:

- operation
- firmware kind
- basename
- byte size
- SHA-256
- board
- target MCU
- privilege class

The public remote operation surface intentionally has no `FULL_ERASE`,
`MASS_ERASE` or raw-memory write operation.

### Application programming

Gateway flow:

`received file -> manifest re-hash -> B300Service.inspect_image -> inspect_target -> build_flash_plan -> B300Service.flash`

`B300Service.flash` remains the authority for:

- S3-S7 erase policy
- Bootloader S0-S2 protection validation
- metadata generation/verification
- target reinspection
- staging/re-hashing
- ST-Link `HardwareMode.FLASHING`
- post-program boot verification

The remote layer does not duplicate or weaken these checks.

### File formats

The transfer manifest accepts `.hex`, `.bin`, `.elf`, `.axf` so the wire
contract does not need to change later. v0.18 execution remains intentionally
limited to Intel HEX because the existing safety-critical address-range parser is
Intel-HEX based. BIN/ELF/AXF execution fails closed until equivalent parser-backed
validation exists.

### Bootloader

Remote Bootloader programming is disabled in v0.18. Local factory provisioning
remains the only supported Bootloader path. A future remote Bootloader workflow
must add an explicit elevated authorization/audit mechanism before it can call the
existing trusted Bootloader factory transaction.

## Preserved invariants

- no mass erase in normal programming
- no normal writes to sectors 0-2
- OpenOCD GDB/TCL never public by default
- only GDB is forwarded to a remote VS Code Client
- Debug/Monitor/Flash remain mutually exclusive through `HardwareSessionManager`
- target run state is checked/restored on GDB disconnect and bridge shutdown
- Live Monitor remains a separate zero-halt workflow
- Interactive debug may halt/step only after explicit user action
- B300 does not become a GDB packet proxy

## Frontend integration boundary

Antigravity should consume the high-level APIs above and must not import or
rebuild the old GDB/MI workstation widgets for the primary production flow.
Legacy internal debugger modules can remain for compatibility/diagnostics while
v0.18 migrates production UX to VS Code.
