# B300 v0.18 — Programmer + Monitor + VS Code Debug Bridge

## Product boundary

B300 v0.18 intentionally is **not a full IDE**. The production surface is:

`PROGRAM / MONITOR / DEBUG / DEVICE / SETTINGS`

B300 remains the ST-Link safety/control plane. VS Code + Cortex-Debug provides
interactive source debugging.

## Clean workstation dependency model

B300 release packages manage the debug backend themselves:

- OpenOCD `0.12.0-7` — B300 bundled/managed
- GNU Arm GDB `15.2.1-1.1` — B300 managed runtime
- ST-Link/host prerequisites — B300 Setup Wizard per operating system

The user installs VS Code and the `marus25.cortex-debug` extension. The Microsoft
C/C++ extension is recommended for IntelliSense/navigation but is not part of the
GDB transport path.

The B300-managed GDB is resolved before a system `PATH` GDB. A custom `B300_GDB`
or explicit GDB path remains available for engineering override. The release
builder downloads a pinned xPack GNU Arm Embedded GCC archive, verifies both the
upstream checksum and B300 SHA-256 trust anchor, performs hardened extraction,
then stages only GDB plus required host runtime/data/license files. GCC/linker and
target libraries are deliberately not shipped as part of the managed debugger
runtime. The staged GDB must pass a build-time startup smoke test before packaging.

Public release still requires the normal third-party redistribution/license
review; retaining upstream notices in the staged runtime is not itself a legal
approval.

## Roles

### LOCAL

`VS Code -> B300 managed GDB -> 127.0.0.1:<gdb> -> OpenOCD -> ST-Link -> STM32F407`

B300 starts OpenOCD on loopback and owns the long-lived `DEBUGGING`
`HardwareSession` lease. B300 keeps a private loopback TCL endpoint only for
`RemoteDebugGuard`, so a target that was running before debug can be resumed if
GDB disconnects while halted. TCL is never exposed to VS Code or the network.

### GATEWAY

`Gateway OpenOCD 127.0.0.1:<gdb> -> ST-Link -> STM32F407`

The Gateway never publishes OpenOCD directly to LAN/Internet. A Client reaches
GDB through authenticated SSH local forwarding. Gateway TCL remains local-only
for run-state restoration.

### CLIENT

`VS Code -> B300 managed GDB -> 127.0.0.1:<local> -> SSH -> Gateway 127.0.0.1:3333 -> OpenOCD`

The Client has source + matching ELF/AXF locally. It does not need ST-Link or a
local OpenOCD installation. B300 opens exactly one loopback GDB forward for the
VS Code bridge; TCL is not forwarded.

## Production frontend integration

`b300_gui.main_window_v18.MainWindowV18` is the v0.18 production entry point.
The DEBUG page is presentation-only and does not directly own subprocesses,
OpenOCD or SSH sessions.

The control path is:

`DebugVsCodeView -> VsCodeDebugController -> VsCodeDebugBridge -> existing DebugService/RemoteSession`

This preserves the existing `HardwareSessionManager` arbitration instead of
creating a second hardware-control path.

Opening or navigating to DEBUG only constructs/renders widgets. It does **not**:

- start OpenOCD/GDB/TCL
- connect SSH
- acquire the ST-Link `DEBUGGING` lease
- reset/halt the target
- touch Flash

LOCAL/GATEWAY/CLIENT activation occurs only after an explicit operator action.
The frontend updates READY state only after the backend operation succeeds.

## Backend API

Primary modules:

- `b300_core.vscode_bridge`
- `b300_core.vscode_environment`
- `b300_gui.vscode_debug_controller`

Key operations:

- `VsCodeDebugBridge.start_local(probe, gdb_port=3333, tcl_port=6666)`
- `VsCodeDebugBridge.start_gateway(probe, gdb_port=3333, tcl_port=6666)`
- `VsCodeDebugBridge.start_client(remote_session, remote_gdb_port=3333, local_gdb_port=0)`
- `VsCodeDebugBridge.profile(...)`
- `VsCodeDebugBridge.stop()`
- `inspect_vscode_environment()`

The controller validates workspace + ELF/AXF and handles `launch.json` conflicts
**before** starting a hardware bridge where possible. If profile generation or
VS Code launch fails after a bridge starts, it stops the bridge so the
`DEBUGGING` HardwareSession lease is not leaked.

## Target run-state guard

LOCAL/GATEWAY use:

- GDB loopback only
- TCL loopback only
- Telnet disabled

After OpenOCD becomes ready, B300 captures initial target state through the
existing `RemoteDebugGuard`. If the board was initially `running` and GDB drops
while the target is `halted`, B300 resumes it. `VsCodeDebugBridge.stop()` performs
a final restoration check before stopping OpenOCD and releasing the hardware
lease.

Window shutdown calls bridge stop before shared-service teardown.

## Cortex-Debug contract

Generated profiles use:

- `type = cortex-debug`
- `request = attach`
- `servertype = external`
- `gdbTarget = 127.0.0.1:<local port>`
- hardware breakpoints required, STM32F407 limit 6
- hardware watchpoints required, STM32F407 limit 4

B300 does not implement source browsing, Watch, Call Stack, Registers,
Disassembly or SVD as a duplicate first-class IDE UI.

## MONITOR

MONITOR is permanently distinct from interactive DEBUG. The v0.18 Monitor page
adopts the existing backend-wired `DebugTab.live_panel` once during window
construction, preserving the proven `LiveMonitorSession` zero-halt path and its
Start/Stop/Clear/Export/symbol wiring. Page navigation never starts monitoring
and never reparents the panel again.

## PROGRAM

Local Application programming reuses the existing B300 flash transaction and
strict Intel HEX parser. The v0.18 frontend accepts Application `.hex` only for
actual execution and does not present BIN/ELF as safely flashable formats.

Local trusted Bootloader factory provisioning remains available as an explicit
privileged action.

### Remote programming foundation

`b300_core.remote_programming` already provides a fail-closed, content-addressed
manifest/safety layer with SHA-256 revalidation and reuse of `B300Service`.
However, end-to-end authenticated Client→Gateway firmware transfer/network
execution is **not complete in v0.18 integration**.

Therefore the production PROGRAM page shows the remote pipeline as a foundation
but keeps Remote Application Flash locked. It must not report an upload/program
success that did not happen. Remote Bootloader programming is also locked.

The remote operation surface intentionally has no `FULL_ERASE`, `MASS_ERASE` or
raw-memory write operation.

## DEVICE

The DEVICE page is evidence-based. Before target inspection it displays
`Chưa kiểm tra` for Device ID, Flash size, VDD, WRP and RDP rather than optimistic
healthy defaults. Target health/protection appears only from `TargetInfo` returned
by the existing backend inspection path.

## Preserved invariants

- no mass erase in normal programming
- no normal writes to sectors 0–2
- Application execution is Intel HEX only until equivalent parser-backed format validation exists
- OpenOCD GDB/TCL never public by default
- only GDB is forwarded to a remote VS Code Client
- Debug/Monitor/Flash remain mutually exclusive through `HardwareSessionManager`
- target run state is checked/restored on GDB disconnect and bridge shutdown
- Live Monitor remains a separate zero-halt workflow
- Interactive debug may halt/step only after explicit user action
- B300 does not become a GDB packet proxy or a duplicate IDE
- remote programming UI fails closed until the network transport is implemented
