# B300 ST-Link Tools v0.14.1 Release Completion Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish v0.14.1 only after the unified frontend/backend, native packages, Windows hardware flash/debug, Ubuntu SSH two-machine workflow, automatic setup, and AI skill have current-version evidence.

**Architecture:** Treat `release/v0.14.1` as the candidate source and keep the B300 Core safety services authoritative for every GUI/CLI operation. Exercise software and packages first, then use the same immutable Application HEX/AXF pair for Windows and SSH field acceptance; publish the immutable tag only after every mandatory gate is recorded.

**Tech Stack:** Python 3.11, PySide6, unittest, PyInstaller, Inno Setup, GitHub Actions, OpenOCD 0.12.0-7, ST-Link/SWD, OpenSSH local forwarding, Minisign.

**Spec:** Thread goal; `AGENTS.md`; `docs/08_RELEASE_ACCEPTANCE.md`; `docs/09_RELEASE_PROCESS.md`; `docs/20_V0.12.0_RC1_TWO_MACHINE_TEST.md`; `docs/superpowers/specs/2026-08-31-gui-frontend-redesign.md`.

## Global Constraints

- Never erase/program Sector 0--2 during normal Application provisioning; only Sector 3--7 belongs to the standard transaction.
- Never use mass/chip erase, modify RDP, bypass HEX validation with raw OpenOCD, retry a failed flash automatically, or run `sudo b300-stlink`.
- Flash only after the owner explicitly authorizes the exact physical board, ST-Link probe, and immutable Application HEX in the current session.
- Remote production debug keeps OpenOCD GDB/TCL on `127.0.0.1`; only SSH TCP/22 is LAN-facing, with strict host-key checking and managed local forwarding.
- Build each native bundle on its own OS/architecture; do not treat source archives as installers.
- Do not commit firmware HEX, AXF/ELF, native OpenOCD binaries, build objects, or release archives.
